- **Feature**: doctor-empty-vault-score (ISSUE-019) — **`mem doctor` não dá mais Health Score 100/100 num vault que nunca foi indexado**. A causa-raiz era a guarda `if report.TotalDocuments > 0`, que pulava o cálculo inteiro e deixava o score no valor inicial `100` — e essa guarda (com a matemática de penalidades **inteira**) estava **duplicada nos dois motores** (`internal/db/graph.go` e `internal/store/doctor.go`). Agora há **uma** regra de aplicabilidade (`store.DoctorReport.HealthScoreApplicable()`) e **uma** função de cálculo (`store.CalculateHealthScore`), usada pelo SQLite e pelo PostgreSQL. Um vault sem documentos indexados não tem denominador para a métrica: o CLI mostra `⚪ … (Health Score: não se aplica)` + a ação (`mem index`), o Markdown do MCP diz o mesmo, e o `health_score` **sai ausente** do `structuredContent` (ausência ≠ 0 ≠ 100; o campo viaja ausente, e não `null`, porque o contrato do wire do `structuredContent` proíbe `null`). A viewer tolera ausência e `null` e mostra "— / vault sem documentos". O caminho com documentos **não regrediu**: 100 perfeito, 90 com 2 dead links, 87 com órfã + self-loop, e o JSON dos vaults com documentos continua byte-idêntico. **Prova contra o defeito:** o defeito foi reintroduzido em 3 pontos e **3 camadas de teste falharam com o sintoma exato**, depois restauradas. **Gate:** `go build`/`go vet`/`go test -count=1 ./...` exit 0 (26 pacotes `ok`), `gofmt -l` vazio, front-end typecheck 0 + **98/98** testes + build 0 + **144.813/163.840 bytes gzip**, e os 3 validadores do fluxo spec-driven sem erro. **Sem ADR nova** — a ADR-013 continua válida; o que mudou é a *precondição de aplicabilidade*, registrada como nota de vigência em `docs/adr/README.md` e no `STATE.md`. Spec: `.specs/features/doctor-empty-vault-score/`. **Pendência (operação, não código):** o vault deste repositório continua efetivamente não indexado (0 documentos) — resolver com `mem index` é decisão do dono.

- **Feature**: repo-id-alignment (ISSUE-028) — **o `mem repos` passou a auditar a identidade de cada entrada do catálogo global**. O `id` do catálogo é a chave que casa o repositório com o override de storage por repositório (`matchesID || matchesPath`); com o `id` divergente do `repo_id`, o casamento passava a depender **só do caminho** — e um repo **clonado ou movido** perdia o override de storage **em silêncio**. Agora o `mem repos` compara o `id` de cada entrada com o `repo_id` declarado no `.memory/config.yaml` do path registrado: divergência vira `❌` + erro explícito com os dois valores, o path e a ação, e **exit ≠ 0**. Entrada sem vault, ou com vault sem `repo_id`, **não** é divergência (não há contra o que comparar) e continua saindo com 0; o formato da tabela não mudou. A auditoria é estritamente **read-only** (provado: bytes do catálogo global e do vault idênticos, nenhum arquivo criado). **Metade A (dado):** o catálogo global (`~/.memory/config.yaml`) foi realinhado de `repo_271444ab0133` para `repo_e4c8f3b1a2d5`, que é o `repo_id` real do repo — com isso o repo **continua casando pelo id** mesmo depois de movido, e o override de storage sobrevive à mudança de path (provado por `internal/config/config_test.go:942`). **Metade B (código):** `cmd/mem/setup.go` (`auditRepositoryCatalog`, `repoIDDivergenceError`, `printRepoIDDivergences`) + `internal/config/config.go:330-396` (`LoadVaultRepoID`, read-only e restrito ao path registrado). **Prova contra o defeito:** dois mutantes injetados no código real mataram o teste `TestRunReposCommand_DivergenciaRepoID` com o sintoma exato. **Gate:** `go build`/`go vet`/`go test -count=1 ./...` exit 0 (26 pacotes `ok`), `gofmt -l` vazio, os 3 validadores do fluxo spec-driven sem erro. **Sem ADR nova** — o cascateamento (ADR-040) e a identidade federada (ADR-033) seguem intocados; a mudança é de diagnóstico. **Sem `mem repos --fix`** (decisão da spec: auto-correção pode agravar o split-brain; fica para feature própria com dry-run + backup, se o dono pedir). Spec: `.specs/features/repo-id-alignment/`.
